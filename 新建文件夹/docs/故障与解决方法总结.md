## 二、线上后台登录失败：HTTP 404

### 现象

本地可以登录，线上登录显示 `CloudBase HTTP 请求失败（404）`。浏览器网络面板记录：

```text
POST https://restaurant-admin-cloud1-d0gzbyfl738d13c13.webapps.tcloudbase.com/restaurant-api
404 Not Found
Content-Type: text/html
```

### 已确认原因

管理端原先配置 `VITE_CLOUDBASE_HTTP_API_URL=/restaurant-api`。本地 Vite 开发服务器会将这个相对路径代理到云函数网关；发布后的静态网站没有这层开发代理，所以请求落到了静态托管域名下不存在的接口路径。

截图中网页本身已经加载成功，失败发生在登录接口请求阶段。这个 404 不能用于判断密码是否正确，也没有证据表明是开启真机调试造成的。

### 已实施修复

新增 `apps/admin/.env.production.local`，生产构建直接使用完整网关地址：

```dotenv
VITE_CLOUDBASE_ENV_ID=cloud1-d0gzbyfl738d13c13
VITE_CLOUDBASE_HTTP_API_URL=https://cloud1-d0gzbyfl738d13c13-1529040983.ap-shanghai.app.tcloudbase.com/restaurant-api
VITE_USE_MOCK=false
```

管理端已重新构建成功。`.env.production.local` 不需要单独上传；配置会在构建时写入前端产物。

### 发布与确认

1. 将 `apps/admin/dist/` 内的全部文件和文件夹上传到静态托管根目录，覆盖旧文件。根目录应直接包含 `index.html` 和 `assets/`。
2. 等待发布完成，按 `Ctrl + F5` 刷新管理端。
3. 登录时查看网络面板，请求应指向上面的完整网关地址。
4. 如果仍发往静态托管域名下的 `/restaurant-api`，说明仍在使用旧构建、旧缓存或上传目录不正确。
5. 若改为完整网关后出现跨域错误，再核对网关针对管理端来源的允许设置，以及 `POST`、`OPTIONS`、`Content-Type`、`Authorization`。404 和跨域错误应分别排查。

**状态：本地配置修复、生产构建完成；最新上传后的线上登录尚未验证。无需为此修改密码或购买域名。**

## 三、提交订单一直提示“请选择份量”

### 现象

红烧肉已经选择规格并加入共享购物车，点击“提交本次点餐”仍提示“请选择份量”，无法进入支付页。

### 已确认原因

云函数加入购物车时保存了按组记录的规格：

```json
[{ "group": "份量", "name": "加大份" }]
```

提交订单再次校验时，却把该数组当作规格名称字符串数组处理，导致有效规格匹配失败。

另外，小程序规格弹窗的内外两层循环原先共用 `item` 变量，内层选项遮蔽外层规格组，影响选中样式和点击参数。

### 已实施修复

- `cloudfunctions/api/index.ts` 的 `makeCartLine` 兼容分组数组、按组对象和旧版名称数组。
- 保留必选、无效选项和重复规格校验；不通过自动选默认规格掩盖错误。
- `miniprogram/pages/menu/index.wxml` 分别使用 `group`、`choice`，正确绑定规格组和选项。
- 现有有效购物车规格可继续提交，无需为这个格式问题清空购物车。

### 验证和部署

本地已复现旧错误，并验证修复后各兼容格式的规格、价格和购物车标识一致；无效、缺失和重复规格仍被拒绝。云函数构建通过。

在微信开发者工具中，上传 `cloudfunctions/api`，选择“上传并部署：云端安装依赖”，确保包含编译后的 `dist/`。随后重新编译小程序，再验证提交后进入支付页。

**状态：本地修复和校验完成；云端更新后的真实提交流程尚待验证。这次不需要为订单规格修复重新发布 Web 管理端。**

## 四、菜单只剩图片，上下架按钮和文字消失

### 现象

管理端菜单卡片只显示菜品照片和“在售”，看不到菜名、价格、编辑、售罄及上下架操作。

### 已确认原因

### 已实施修复

- 固定图片显示范围，使用定位和裁切限制图片尺寸。
- 让卡片正文正常显示，按钮区支持换行。
- 保留“编辑”“设为售罄 / 恢复售卖”“上架 / 下架”功能。

### 验证和发布

已在连接云端的本地管理端验证：拍黄瓜下架后显示“已下架”，重新上架成功，已恢复原来的在售状态。六道菜的名称、价格和按钮已正常显示。

线上显示修复需重新上传最新 `apps/admin/dist/`，再强制刷新。

## 五、分类筛选无效、菜品显示“未分类”

### 已确认原因

1. 原分类标签只是 `span`，没有绑定点击筛选。
2. `admin.overview` 返回分类的 `_id`，页面却使用 `id`，造成分类匹配和编辑下拉框绑定异常。

### 已实施修复

- 分类标签改为按钮，增加“全部”、当前选中状态和分类筛选。
- `apps/admin/src/api.ts` 统一分类 ID，兼容旧云函数返回。
- 云函数概览接口同步将分类 `_id` 映射为 `id`。
- 搜索和分类筛选可以同时使用。

已验证“饮品”只显示酸梅汤、柠檬茶、鲜榨橙汁，编辑菜品时显示正确所属分类。

**发布说明：管理端已兼容旧格式，上传最新 `dist` 即可使用该兼容修复；云函数对应修改可随下一次部署一并更新。**

## 六、云函数上传失败

### `ResourceNotFound.Function`

```text
未找到指定的Function，请创建后再试。
```

这表示当前上传操作找不到目标函数。应检查所选环境、函数名称 `api`，以及函数是否已创建。不存在时先创建，再上传代码；不要持续对不存在的函数执行更新。

### `FailedOperation.UpdateFunctionCode` / `CreateFailed`

```text
当前函数处于CreateFailed状态，无法进行此操作。
```

说明函数创建失败，不能直接更新代码。需查看控制台中的创建失败详情，核对运行时、入口和代码包后修复或重新创建。历史日志未包含创建失败详情，因此不能认定当时的底层原因。

用户后来确认已部署成功；上述历史报错不代表当前函数仍处于失败状态。

### 构建和上传约定

```powershell
npm run build:function
```

上传整个 `cloudfunctions/api/`，包括 `package.json`、入口文件及 `dist/`。本项目根入口 `index.js` 会加载 `dist/index.js`；需确保控制台实际入口与上传文件保持一致。只改 TypeScript 而没有重新构建，可能上传的仍是旧逻辑。

## 七、数据库缺少集合、菜单或桌台没有显示

曾出现：

```text
[ResourceNotFound] Db or Table not exist: staff
```

该错误明确表示当前请求所用数据库中找不到 `staff` 集合。检查实际访问环境是否为 `cloud1-d0gzbyfl738d13c13`，再检查集合是否存在；在另一个环境建集合不能解决当前环境的问题。

项目部署文档列出的业务集合为：

```text
users, staff, categories, dishes, tables, diningSessions, orders, auditLogs
```

当前受控管理员初始化流程可补建缺失集合；若云端仍是旧版实现，需部署新版后再执行相应初始化。

菜单不显示还应区分以下情况，不能一律归因于缺少桌台：

- 菜单接口失败：查看云函数返回的具体错误。
- 菜品或分类为空：检查对应集合和业务数据。
- 菜品下架：检查 `active`；售罄检查 `soldOut`。
- 分类关联不正确：核对 `categoryId` 与分类记录 ID。
- 桌台或桌次无效：检查当前桌台及开放桌次，再重新选桌。
- 使用了模拟数据：检查小程序配置的 `mock` 与管理端 `VITE_USE_MOCK`。

历史中用户补充过集合和桌台，但缺少每次故障的完整响应，以上其余条目属于排查清单。

## 八、管理员、前台、后厨账号与初始化口令

默认用户名为 `admin`、`frontdesk`、`kitchen`，具体用户名可由云函数环境变量配置。

| 配置 | 用途 |
| --- | --- |
| `ADMIN_BOOTSTRAP_USERNAME` | 管理员用户名，默认 `admin` |
| `ADMIN_BOOTSTRAP_PASSWORD` | 管理员初始化或恢复口令 |
| `FRONTDESK_BOOTSTRAP_USERNAME` | 前台用户名，默认 `frontdesk` |
| `FRONTDESK_BOOTSTRAP_PASSWORD` | 初始化前台账号的口令 |
| `KITCHEN_BOOTSTRAP_USERNAME` | 后厨用户名，默认 `kitchen` |
| `KITCHEN_BOOTSTRAP_PASSWORD` | 初始化后厨账号的口令 |
| `SESSION_SECRET` | 服务端会话签名密钥 |

员工密码以哈希形式保存在 `staff` 集合，网页中不应存放真实密码。初始化口令不是一套对所有环境都通用的固定密码，本文不记录实际密码或密钥。

当前实现中，管理员可通过受控的“初始化管理员”入口使用配置的初始化口令创建或恢复账号。恢复会重设对应管理员密码，并要求改密；这是账号恢复操作，不应作为每次登录的常规步骤。

排查顺序：先确认接口可达 → 检查业务错误 → 检查集合和账号 → 必要时执行受控恢复。HTTP 404 时不应先重置密码。

## 九、扫码方案受限与最终调整

曾出现微信小程序码生成错误：

```text
openapi.wxacode.getUnlimited:fail personal entity not verified
```

该次请求被微信接口以主体未验证为由拒绝，不是单纯生成二维码图片失败。第三方工具生成普通二维码图片，不能直接证明具备微信扫码打开指定小程序页面的能力。

最终按用户确认取消扫码入座和生成二维码，改为打开小程序先选择桌台，再进入菜单。后续无需围绕 `getUnlimited` 排查当前选桌流程。

## 十、其他历史报错与限制

| 现象 | 解释及处理 |
| --- | --- |
| WXSS `Unknown word` | 属于样式语法错误；当时片段末尾出现孤立的 `.`。检查报错位置，移除残缺规则并重新编译。没有完整历史文件，不能进一步确认当时全部修改。 |
| 同步云环境列表时 TLS 连接中断 | 日志显示开发者工具同步环境列表的网络连接未完成。先排查网络、代理和工具连接；仅凭这条日志不能认定数据库或业务函数出错。 |
| 开发工具资源 preload 未使用警告 | 不能仅凭该警告判定业务失败，应优先查看真正失败的云函数请求及错误。 |
| 图片生成因未配置密钥暂停 | 当时缺少可用生图凭据；之后六道菜图片已通过可用生图工具生成、上传云存储并应用到云端菜品。当前管理端图片遮挡属于布局问题。 |
| 图片上传 HTTP 413 | 先前图片上传请求体过大；图片压缩为约 30–49 KB 的 480 像素 JPEG 后完成上传。 |
| 本地构建 `spawn EPERM` | 本次执行环境限制了构建子进程。获准在限制外构建后成功，不代表项目代码一定存在编译错误。 |

## 十二、建议的故障定位顺序

1. 记录出现问题的页面、操作和准确报错。
2. Web 查看网络面板的请求 URL、方法、状态码和响应；小程序查看 `wx.cloud.callFunction` 的返回及云函数日志。
3. 404 优先核对域名和路由；网络或跨域错误检查请求链路；业务错误再检查账号、数据和状态校验。
4. 确认是在本地还是线上、是否有本地代理、是否调用同一 CloudBase 环境。
5. 修复后构建对应产物，部署到正确位置，最后验证云端结果。
